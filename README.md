Windows PC의 CPU / GPU / RAM / 저장장치 / 네트워크 / 디스플레이 / 드라이버 상태를
한 번에 진단하고, 마우스·키보드·모니터·인터넷 개별 테스트까지 한 앱에 통합했습니다.

기획서의 "AI 진단 엔진"은 실제로는 **임계값 + 상관관계 규칙(rule-based) + 판단 근거 강도 점수**로
구현되어 있습니다 (`src/engine/rules.js`). 머신러닝 모델이 아니라 사람이 정한 규칙이지만,
동작 흐름(측정 → 분석 → 진단 → 근거 제시 → 조치 제안)은 기획 의도와 동일합니다.

**핵심 원칙**: 검사하지 않은 것을 정상이라고 하지 않습니다. 판단할 수 없으면 "판단 보류"로
남기고, 관측한 사실과 추정한 원인을 분리해서 표시합니다.

## 다운로드 (Windows)

**[→ 공식 사이트에서 받기](https://thisismo0614.github.io/DIAG.BENCH/download.html)**
— 최신 버전과 SHA-256 체크섬을 함께 안내합니다.

<sub>GitHub에서 직접 받으려면 [릴리스 목록](../../releases)을 보세요.
현재 0.x는 전부 사전 릴리스로 발행되므로 `releases/latest`는 목록으로 넘어갑니다.</sub>

공식 배포는 **GitHub Releases**에서만 이루어집니다. 다른 경로로 배포되는 파일은
이 프로젝트와 무관합니다.

| 항목 | 값 |
|---|---|
| 지원 OS | Windows 10 (x64) 이상 |
| 아키텍처 | x64 전용 (32비트·ARM 미지원) |
| 형식 | 설치 프로그램 (설치 위치 지정 가능) |
| 가격 | 무료 · 오픈소스 (MIT) |

### 파일 무결성 확인

릴리스마다 `SHA256SUMS.txt`를 함께 배포합니다. 내려받은 파일이 배포된 것과 같은지
직접 확인하실 수 있습니다.

```powershell
Get-FileHash ".\DIAG.BENCH-Setup-<버전>-win-x64.exe" -Algorithm SHA256
```

### 코드 서명과 Windows 보안 경고

각 릴리스의 **서명 여부는 릴리스 노트에 명시**됩니다. 서명된 빌드는 직접 확인할 수 있습니다.

```powershell
Get-AuthenticodeSignature ".\DIAG.BENCH-Setup-<버전>-win-x64.exe"
```

> ⚠ **코드 서명과 Windows SmartScreen 평판은 별개의 시스템입니다.**
> 코드 서명은 "누가 배포했고 변조되지 않았는가"를 확인해주고, SmartScreen 평판은
> 다운로드·실행 이력이 쌓이면서 따로 형성됩니다. 따라서 **서명이 있어도 새 버전에는
> 한동안 경고가 표시될 수 있습니다.** 가장 확실한 확인 방법은 위의 SHA-256 비교입니다.

## 개발

```
npm install
npm start              # 앱 실행
npm run test-rules     # 회귀 테스트 130개
npm run test-engine    # GUI 없이 진단 엔진 결과만 콘솔 출력
npm run build:win      # Windows 설치 파일 생성 → dist/
```

빌드에는 Windows 환경이 필요합니다(electron-builder NSIS).

### 배포

버전 태그를 push하면 빌드 → 코드 서명 → 릴리스가 자동으로 진행됩니다.

```bash
git tag v0.18.0
git push origin v0.18.0
```

자세한 설정 방법과 최초 1회 준비 작업은 **[docs/RELEASING.md](docs/RELEASING.md)** 를 참고하세요.

### 공식 웹사이트

`website/` 폴더에 정적 사이트 소스가 있습니다. `main`에 push하면 GitHub Pages로 자동
배포되며, 새 릴리스가 나오면 다운로드 링크와 버전이 자동으로 갱신됩니다.

```bash
cd website && node build.js    # dist/ 에 생성
```

## 실제 Windows PC에서 발견되고 고친 것

- **BIOS 더미 플레이스홀더 오탐 수정** — 실제 조립 PC(Gigabyte 보드)에서 테스트해보니 "시스템 시리얼"에 `To be filled by O.E.M.`이라는 텍스트가 그대로 찍혀서, 마치 진짜 시리얼인 것처럼 보였습니다. 이건 메인보드 제조사가 비완제품(조립 PC)에 흔히 남겨두는 더미 텍스트입니다. `To be filled by O.E.M.`, `Default string`, `System manufacturer`, `None`, `N/A` 등 알려진 플레이스홀더 패턴을 걸러내도록 고쳤고, 조립 PC에서는 시스템 시리얼이 원래 없는 경우가 많다는 안내 문구도 추가했습니다. **GPU UUID와 저장장치 시리얼은 실제 PC에서 정상적으로 잡히는 것을 확인했습니다.**

## 이번 버전에서 새로 생긴 것

- **평소 상태 기준선 (Baseline)** — 절대 임계값만으로는 "이 PC에서 뭔가 달라졌다"를 잡을 수 없습니다. 유휴 CPU 온도 58°C는 어떤 PC에서는 정상이고 어떤 PC에서는 이상인데, 절대 임계값(85/95°C)은 둘 다 통과시킵니다. 먼지 누적·쿨러 열화처럼 **서서히 나빠지는 문제**는 "이 PC는 평소 44°C였다"는 정보가 있을 때만 보입니다. 아무 작업도 하지 않는 유휴 상태를 33초간 측정해 기록해두고(`baseline.js`, userData의 `baseline.json`), 다음 진단부터 "평소 44°C → 지금 60°C(+16°C)"처럼 비교합니다. 만들면서 실측으로 확인하고 막은 것들:
  - **부하 상태를 "평소"로 굳히지 않는다** — 게임 중에 기준선을 뜨면 "평소 온도 78°C"가 되어 진짜 문제가 생겨도 정상으로 보이게 됩니다. 샘플의 75% 이상이 유휴 범위(CPU 20% 이하)일 때만 기준선으로 인정하고, 아니면 **저장하지 않고 이유를 알려줍니다**("샘플 12개 중 4개만 유휴였고 최고 부하는 53%"). "측정을 실행했다"와 "측정이 유효했다"는 다릅니다.
  - **부하 중에는 유휴 기준선과 비교하지 않는다** — 게임 중 CPU 78°C를 유휴 기준선 44°C와 비교하면 "+34°C 이상"이 되는데 이건 고장이 아니라 그냥 부하입니다. 지금이 유휴 범위 밖이면 비교 자체를 건너뛰고 "부하가 걸린 상태라 비교하지 않았습니다"라고 근거 줄에만 남깁니다. 정상이라고도, 이상이라고도 하지 않습니다.
  - **첫 샘플은 버린다 (실측으로 찾은 함정)** — `si.currentLoad()`는 "직전 호출 이후"의 평균이라, 캡처 시작 후 처음 읽는 값은 그 앞의 긴 공백을 통째로 포함해 크게 부풀려집니다. 같은 조건에서 **#0=46%, 이후 #1~#9=11~16%**로 측정됐고, 이 한 샘플 때문에 멀쩡한 유휴 PC에서도 측정이 절반쯤 거부됐습니다. 기준점만 잡고 버리도록 고친 뒤 유휴 샘플이 **10/10**으로 안정됐습니다.
  - **진단 본작업 전에 비교용 스냅샷을 뜬다** — 진단이 시작되면 이 앱 자신이 PowerShell·nvidia-smi·SMART 조회를 돌리느라 CPU를 크게 씁니다(실측: 4코어 Xeon에서 **37~45%**). 그 값으로 "지금 유휴인가"를 판단하면 진단할 때마다 비교가 통째로 건너뛰어져 기능이 사실상 죽습니다. 본작업 **전**에 조용한 상태를 한 번 떠서(같은 시점 스냅샷 **5~9%**) 그걸로 비교합니다.
  - **하드웨어가 바뀌면 쓰지 않는다** — CPU 모델이 다르면 다른 PC의 기준선이므로 비교를 건너뜁니다. GPU만 바뀌었으면 GPU 항목만 건너뛰고 CPU 비교는 유지합니다.
  - **오래됐다고 버리지 않는다** — 유효기간을 두면 정작 "몇 달에 걸쳐 나빠지는 변화"를 못 잡습니다. 대신 나이를 함께 표시하고(180일 이상이면 그동안 실내 온도가 달라졌을 수 있다고 명시) 신뢰도를 낮춰 잡습니다.
  - **원인을 하드웨어 고장으로 단정하지 않는다** — 실내 온도(계절)와 직전 작업의 잔열이 똑같은 신호를 만듭니다. 그래서 원인 후보 맨 앞에 그 둘을 적고, 신뢰도를 60 이상으로 올리지 않습니다. 10°C 차이는 watch(지켜보기), 실내 온도만으로 설명하기 어려운 15°C부터 warning입니다.
- **판매용 점검 리포트** — 중고 거래·재판매 시 구매자에게 넘겨줄 수 있는 문서를 만듭니다. "인증서"라는 단어는 의도적으로 쓰지 않았습니다(중소벤처기업부의 "성능인증(EPC)" 제도와 혼동 방지).
  - **등급 시스템** — A+/A/B/C/D (부하 테스트까지 포함해서 이상 없으면 A+, 기본 검사만 통과하면 A)
  - **영역별 점수** — Hardware Health / Thermal Condition / Storage Health / Stability / Software Condition을 따로 표시
  - **"검사 완료"와 "고장 없음"을 명확히 구분** — 부하 테스트(CPU/저장장치/RAM)는 기본적으로 실행하지 않으며, 안 돌린 검사는 PASS가 아니라 "검사 안 함"으로 명시합니다. "정밀 검사 포함" 체크박스를 켜면 실제로 부하 테스트까지 돌리고 그 항목들이 "검사 완료" 목록으로 이동합니다.
  - **하드웨어 시리얼 바인딩 + 마스킹** — 시스템/메인보드/저장장치 시리얼, GPU UUID(NVIDIA)를 기록하되, 공개 문서로 공유될 수 있다는 점을 고려해 뒤 4자리만 보여주고 나머지는 마스킹합니다(위변조 감지용 해시는 마스킹 전 원본 값으로 계산되어 정확도에 영향 없음).
  - **위변조 감지 코드** — 하드웨어 식별값+점검결과를 SHA-256으로 해시. 값 하나만 바뀌어도 검증에 실패하는 것을 테스트로 확인했습니다.
  - **유효기간 표시** — 발급 후 7일
  - **면책 문구** — "법적 인증서가 아니며 정부 성능인증 제도와 무관하다", "검사 범위 밖 항목은 확인되지 않았다"는 문구를 리포트 본문에 명시
  - QR코드는 완전히 로컬에서 생성됩니다(서버 없음, 오프라인 동작)
  - **앱 화면 = 저장 파일** — 앱에서 보여주는 결과 화면과 저장되는 파일이 서로 다른 템플릿이 아니라 완전히 같은 HTML(`inspectionReportHtml.js`)이다. 화면에서는 그 HTML을 iframe으로 그대로 보여주고, 저장할 때는 HTML/PDF 중 사용자가 고른 형식으로 저장한다(PDF는 같은 HTML을 숨긴 창에 띄워 `webContents.printToPDF`로 인쇄). PDF는 상세설명을 강제로 펼쳐서 저장하고, HTML은 화면처럼 접은 채로 저장해 저장 후에도 클릭해서 펼칠 수 있다.
  - **근거 상세설명 토글** — 각 검사 항목이 왜 정상/이상으로 판정됐는지(측정값, 원인, 조치, 재검사 방법)를 `<details>`로 접어두고 "상세설명"을 누르면 펼쳐지도록 해서, 요약은 한눈에 보이면서도 필요하면 근거를 전부 볼 수 있다.
  - **"영역별 점검 결과"도 상세설명 지원** — Hardware Health/Thermal Condition/Software Condition은 CPU/GPU/RAM/저장장치/드라이버/이벤트 중 "가장 나쁜 상태"만 가져온 요약 점수라 배지만 봐서는 왜 그 등급인지 알 수 없었다. 이제 각 점수를 펼치면 실제로 근거가 된 세부 항목(explanation/근거/원인/조치)을 그대로 보여준다. Stability는 정밀 검사를 돌렸을 때 CPU 부하/저장장치 처리량/RAM 검사의 실제 수치까지 펼쳐서 보여준다.
- **Windows 이벤트 로그 연동** (WHEA/블루스크린/재부팅/드라이버크래시)
- **Display 셀프체크 → 진단 엔진 연동** — 불량화소/잔상/균일도는 소프트웨어가 자동으로 판정할 수 없어(사람 눈으로만 확인 가능) 지금까지는 진단과 분리된 도구였다. 이제 사용자가 "이상 없음/이상 발견"을 직접 기록하면(`displayChecks.js`) 그 결과가 DISPLAY 진단 섹션의 근거로 반영되고, 진단 리포트/점검 리포트에도 함께 나타난다.
- **Correlation Engine — 카테고리 간 상관관계** — CPU/GPU의 온도↔클럭 추이 분석은 원래 있었지만, 서로 다른 카테고리끼리는 각자 따로 판정했다. 이제 오늘 측정한 라이브 상태(CPU/GPU 열 스로틀링, 저장장치/메모리 이상)와 최근 며칠간의 Windows 이벤트 로그(예기치 않은 종료, 그래픽 드라이버 TDR, WHEA, 디스크 오류)를 서로 대조해서, **둘 다 있을 때만** 서로를 근거로 추가하고 신뢰도를 높인다(`applyCorrelations` in `rules.js`). 한쪽만 있으면 아무것도 하지 않아 근거 없는 확신을 만들지 않는다.
- **실시간 모니터링 (Live Monitoring)** — CPU/GPU/RAM 사용률·온도·클럭을 1초 간격으로 갱신하며 최근 1분을 그래프로 보여준다. 메인 프로세스가 폴링을 돌리고(`collectLiveSample()` — 진단용 `collectCpu`/`collectGpu`와 달리 정적 정보 없이 가벼운 값만 읽음, 이 PC 기준 1회 850ms) 화면을 벗어나면 반드시 폴링을 멈춘다(`stop-live-monitor`) — 실측으로 확인함. **센서 기록(Sensor Recording)**: "기록 시작"을 누르면 그 구간의 값을 타임스탬프와 함께 로그로 남기고 JSON으로 저장할 수 있다(문제가 발생하는 순간을 붙잡아두는 용도).
- **GPU 부하 테스트(안전장치 포함)** — "CUDA/DirectX 없이는 실제 GPU 부하를 못 만든다"고 이전 버전에서 명시적으로 제외했던 항목인데, 이 세션에서 실측으로 뒤집혔다: Electron이 곧 Chromium이라 WebGL 렌더링이 실제 GPU 하드웨어 가속을 쓴다. 무거운 프래그먼트 셰이더를 렌더러 창에 그리면 CUDA 없이도 `nvidia-smi`로 측정되는 진짜 GPU 부하가 생긴다(유휴 28% → 렌더링 중 51~58%, 실제 앱에 붙여서도 확인). 10%→30%→50%→75%→90%→100%로 단계적으로 부하를 올리며(각 3초) 실시간 모니터링과 같은 `live-sample` 인프라로 온도·클럭·VRAM을 추적하고, 안전 한계(90°C) 초과 시 자동 중단한다. 최고 부하 구간에서 온도 상승+클럭 하락이 함께 확인되면 열 스로틀링 의심으로 판정(CPU/GPU 트렌드 판정과 같은 방식).
- **VRAM 압박 · 무결성 테스트** — GPU 부하 테스트가 GPU "코어"를 바쁘게 만드는 것이라면, 이건 GPU "메모리"를 확인한다. 2048x2048 RGBA8 텍스처(타일당 16MB)를 여유 VRAM의 60%까지 올린 뒤, 각 타일을 프레임버퍼에 붙여 `readPixels`로 되읽어 32비트 워드 단위로 비교한다. 1패스는 원본 패턴, 2패스는 같은 패턴의 비트 반전 — 특정 비트가 0이나 1로 고착돼 있으면 두 패스 중 한 번은 반드시 걸리게 하기 위해서다. 실측으로 확인한 것:
  - **되읽기는 바이트 단위로 정확하다** — 정상 GPU에서 1GB × 2패스에 불일치 0. 색공간 변환이나 프리멀티플라이 같은 오탐 요인이 끼어들지 않는 것을 먼저 확인하고 나서 이 기능을 넣었다(오탐이 나면 멀쩡한 GPU를 고장났다고 말하게 되므로).
  - **할당 성공량은 VRAM 용량이 아니다** — 여유 1.8GB인 카드에 2.6GB를 요청했더니 **할당이 그냥 성공했다**(OUT_OF_MEMORY 안 남). Windows가 넘치는 만큼을 시스템 메모리에 얹기 때문이다. 그래서 이 테스트는 할당량을 믿지 않고, `nvidia-smi` 기준 VRAM 사용량이 실제로 그만큼 올라갔는지를 함께 보고 **증가분 기준으로만 "검사했다"고 말한다**. 증가가 거의 없으면 불일치가 0이어도 "정상"이 아니라 **판단 보류**로 표시한다.
  - **끝나면 VRAM을 반드시 반납한다** — `deleteTexture`만으로는 `nvidia-smi` 사용량이 돌아오지 않는 것을 실측으로 확인해서, 테스트마다 캔버스/컨텍스트를 새로 만들고 끝나면 `WEBGL_lose_context`로 컨텍스트째 버린다(1277MB → 2619MB → 1248MB 복귀 확인).
  - 테스트 도중 그래픽 컨텍스트가 손실되면 드라이버 리셋/TDR 가능성으로 따로 표시한다.
  - **진단 엔진 연동** — 검사 결과는 화면에만 남지 않고 기록되어(`vramChecks.js`, 30일 유효) 다음 전체 진단의 GPU 근거로 들어간다. 불일치·컨텍스트 손실은 GPU 이슈(warning)로 올리되 원인을 하나로 단정하지 않고(셀 불량/오버클럭/드라이버/과열을 후보로 나열), 최근 Windows 이벤트 로그에 그래픽 드라이버 TDR이나 WHEA가 **함께** 있을 때만 서로를 근거로 보강한다. **판단 보류로 끝난 검사는 이슈로 올리지도, 정상으로 묻지도 않고 "판단 보류 + 사유"를 근거 줄로 남긴다.** 판매용 점검 리포트에서는 검사 완료 항목에 실행일과 실제 확인 범위(예: "전체 3072MB 중 1056MB")까지 적어서, 구매자가 "VRAM 전체가 검증됐다"고 오해하지 않게 한다.
- **GPU 부하 테스트 → 진단 엔진 연동, 그리고 부하 생성 자체를 고침** — VRAM 검사와 같은 방식으로 결과를 기록해(`gpuStressChecks.js`, 30일 유효) 다음 진단의 GPU 근거로 넘긴다. 스로틀링·안전 한계 온도 중단은 GPU 이슈로 올리고, 이벤트 로그의 TDR/예기치 않은 종료와 **둘 다 있을 때만** 서로 근거로 보강한다. 연동하면서 실측하다 두 가지를 발견해 함께 고쳤다:
  - **부하가 제대로 안 걸리고 있었다.** 화면 주사율(vsync) 때문에 rAF는 초당 60프레임으로 묶이는데 프레임당 한 번만 그리면 GPU가 프레임 사이에 놀아버린다. 프레임당 드로우 콜 수를 바꿔가며 측정하니 **1회 29% / 4회 58% / 16회 99%**(전부 65fps 유지)여서 16회로 정하고, 프레임마다 `gl.finish()`로 동기화해 명령이 무한정 쌓이지 않게 했다. 같은 PC에서 실제 테스트 최고 부하가 **15% → 100%**로 바뀌었다(온도 42→53°C, 클럭 607→1860MHz).
  - **"부하 테스트는 돌았는데 GPU는 논" 상태를 정상으로 기록하고 있었다.** 창을 최소화하거나 완전히 가리면 화면 갱신이 멈추는데, 그때도 "완주, 이상 없음"으로 기록됐다. 이제 실제 관측된 최고 사용률이 50% 미만이면 정상이 아니라 **판단 보류**로 처리하고 이유를 알려준다. 진단 근거와 점검 리포트에도 "실제 최고 사용률 몇 %"를 함께 적어서, 얼마나 세게 돌린 검사인지 읽는 사람이 판단할 수 있게 했다.
- **⚠ 실제 사용자 PC에서 발견된 오탐 수정 — "비정상 종료 19회"는 사실 정상 절전이었다** — 이벤트 로그를 provider 이름(`Kernel-Power`)만으로 분류하고 있었는데, 이 provider에는 진짜 비정상 종료(ID 41)뿐 아니라 **절전 진입(42)·절전 복귀(107)·정상 종료 전환(109)·최신 대기모드(131/172/187)** 이벤트가 전부 들어옵니다. 그걸 다 세는 바람에 멀쩡한 PC가 "최근 7일 비정상 종료 19건"으로 표시되고 등급까지 C로 내려가 있었습니다. 이제 **이벤트 ID로 판별**하며, 같은 PC를 다시 진단하니 비정상 종료 0건 · 등급 A+로 바뀌었습니다. 판정에서 제외한 전원 이벤트 건수도 근거에 남겨서, 다른 도구에서 "이벤트 수십 건"을 보고 온 사용자가 왜 여기선 조용한지 알 수 있게 했습니다. WHEA도 **정정된 오류(하드웨어가 스스로 복구, 흔함)** 와 **정정 불가 오류**를 구분해, 정정된 것만 있으면 critical이 아니라 "지켜볼 항목"으로 처리합니다.
- **정밀 검사 결과가 최종 등급에 실제로 반영됩니다** — 이전에는 부하 테스트 결과가 리포트에 숫자로만 찍히고 진단 엔진에는 전달되지 않아서, **RAM 검사에서 오류가 나와도 최종 등급이 정상으로 나올 수 있었습니다.** 이제 `측정 → 규칙 엔진 → 이슈 → 등급 → 리포트`가 하나로 이어집니다.
  - RAM 불일치 → critical (백업·XMP 해제·MemTest86 교차 확인 안내), 저장장치 쓰기/읽기 데이터 불일치 → critical, I/O 오류 → warning, CPU 안전 온도 도달 → warning
  - **속도만으로는 고장이라고 하지 않습니다** — 저장장치 처리량은 HDD/SATA SSD/NVMe에 따라 수십 배 차이라 임계값 판정이 불가능합니다. 측정값만 남기고, I/O 실패·데이터 불일치처럼 장치 종류와 무관한 이상만 이슈로 올립니다.
  - 부하 테스트가 실패해도 예외를 던지지 않고 실패를 결과로 남깁니다 — "검사 안 함"과 "검사했는데 실패"가 섞이면 안 되기 때문입니다.
- **CPU 온도 센서가 없는 환경을 정직하게 처리** — 센서를 못 읽으면 온도 기반 자동 중단이 불가능합니다. 그때 "안전장치가 동작한다"고 말하지 않고, 시간 제한(최대 30초) 안전 모드로 전환한 뒤 그 사실을 화면·진단 근거·리포트에 명시합니다.
- **위변조 감지 해시가 리포트 내용 전체를 덮습니다** — 이전에는 하드웨어 식별값과 카테고리 상태(정상/주의)만 해시해서, 근거 문구나 부하 테스트 측정값이 바뀌어도 검증이 통과하는 구멍이 있었습니다. 이제 각 이슈의 근거·원인·조치, 부하 테스트 원자료, 검사 범위, 최종 등급까지 포함해 계산합니다(canonical JSON — 키 순서가 달라도 같은 해시). 생성과 검증이 같은 함수를 쓰고, RAM 오류 개수 하나만 바꿔도 검증이 실패하는 것을 테스트로 고정했습니다. **리포트 번호(식별용)와 검증코드(무결성)의 역할도 분리**해서, 내용이 정정돼도 번호는 유지되고 검증코드만 바뀝니다.
- **등급만 보고 오해하지 않도록** — 등급 글자 아래에 "이 등급의 이유(어느 항목 때문인지)"와 "정상으로 확인된 영역"을 항상 함께 표시합니다. 하드웨어는 멀쩡한데 이벤트 기록 하나 때문에 C가 되는 경우가 흔하기 때문입니다. 검사 범위도 "기본 8건 완료 · 정밀 3건 완료, 1건 미검사 (미검사 항목은 정상으로 집계하지 않았습니다)"처럼 요약합니다.
- **부하 테스트 파라미터를 메인 프로세스에서 다시 검증** — Electron에서 렌더러는 신뢰 경계 밖입니다. UI에서 제한하더라도 메인 프로세스가 한 번 더 범위를 강제합니다(CPU 5~300초, 저장장치 50~2048MB, RAM 64~1024MB). 실제로 100GB RAM 검사나 4TB 저장장치 테스트를 요청해도 상한으로 접히는 것을 확인했습니다. 테스트 파일 경로도 렌더러가 정할 수 없습니다.
- **이벤트 로그가 개수 제한에 잘리지 않습니다** — 예전에는 전체를 시간순으로 정렬해 앞 50건만 가져와서, 특정 provider 이벤트가 많으면 다른 계통(WHEA 등)이 통째로 잘려 "0건"으로 오판될 수 있었습니다. 이제 provider/ID별 전체 건수는 따로 집계하고, 화면에 보여줄 목록만 제한합니다.
- **"신뢰도" → "판단 근거 강도"** — 확률처럼 오해될 수 있어 명칭을 바꿨습니다. 실제로는 통계 모델이 아니라 근거의 개수와 일치도로 계산한 규칙 기반 점수이며, 그 사실을 화면에 함께 표시합니다.
- **fixture 기반 회귀 테스트** — 정상 PC / RAM 오류 / 저장장치 실패 / CPU 과열 / GPU 스로틀링 / SMART 실패 / 비정상 종료 / 절전 이벤트 오탐 / 여러 문제 동시 발생 등 16개 시나리오를 "이 상태면 이 등급"으로 고정했습니다. 특히 **정밀 검사에서 문제가 나왔는데 A/A+ 등급이 나오는 회귀**를 직접 막는 테스트를 넣었습니다.
- **SMART 상세 속성 분석 — "PASSED인데 죽어가는 디스크"를 잡습니다** — 지금까지는 SMART 전체 판정(PASSED/FAILED)만 봤습니다. 그런데 이 값은 **디스크가 거의 죽어야 FAILED로 바뀝니다.** 수리 현장에서 실제로 보는 건 개별 속성값입니다. 이제 `smartctl -A`까지 읽어 판정합니다.
  - **읽기 실패 섹터(Current_Pending_Sector)** — 전체 판정이 PASSED여도 이 값이 0보다 크면 경고합니다. 완전 고장 전에 먼저 올라가는 신호로 알려져 있어, 전체 판정보다 빨리 문제를 알려줍니다. 10개 이상이면 critical.
  - **재할당 섹터** — 소수는 사용 중인 디스크에서 드물지 않아 watch로만 두고, 50개 이상일 때 warning. "개수가 늘어나는지"가 판단의 핵심이라는 점을 안내에 명시합니다.
  - **CRC 오류는 디스크 고장으로 취급하지 않습니다** — 이건 대개 **케이블/연결 문제**입니다. 같은 심각도로 다루면 멀쩡한 디스크를 교체하게 만들기 때문에, 따로 구분하고 "SATA 케이블 교체를 먼저 시도"하도록 안내합니다.
  - **SSD 수명** — NVMe 예비 영역이 제조사 임계값 이하면 critical, 쓰기 수명 100% 초과는 warning(단, "수명 소진 = 즉시 고장"으로 단정하지 않습니다). NVMe critical warning 플래그, 미디어/무결성 오류도 반영합니다.
  - **제조사 자신의 기준(WHEN_FAILED)** — 속성이 제조사가 정한 임계값 아래로 떨어지면 critical. 이건 우리가 정한 기준이 아니라 디스크 제조사의 기준입니다.
  - **중고 거래용 맥락 정보** — 사용 시간을 연 단위로 환산(예: "36,523시간 = 약 4.2년치 가동"), 전원 켠 횟수, 누적 쓰기량을 점검 리포트에 **측정값 원본 그대로 표**로 싣습니다. 구매자가 가장 알고 싶어하는 값이고, 판매자의 "괜찮다"는 말보다 숫자가 찍힌 문서가 훨씬 쓸모 있기 때문입니다.
  - ⚠ NVMe는 이 PC의 실제 디스크로 검증했지만, **SATA/HDD 형식은 장비가 없어 샘플 출력으로만 검증**했습니다. 실제 SATA가 있는 PC에서 확인이 필요합니다.
- **⚠ 고장난 디스크에서 결과를 못 읽던 버그 수정** — smartctl은 종료 코드를 비트마스크로 쓰는데(bit3 = "DISK FAILING"), 기존 실행 함수가 종료 코드 0이 아니면 출력을 통째로 버리고 있었습니다. 즉 **정작 디스크가 고장났을 때 "판독 불가"로 표시**될 수 있었습니다. smartctl 전용 실행 함수로 분리해 종료 코드와 무관하게 출력을 살립니다.
- **판단 보류(watch) 상태, SMART 미지원/이상 구분, 자동 규칙 테스트(130개), Severity/판단 근거 강도 시각적 분리**
- **진단 전/후 비교(부하 지표는 개선/악화로 단정하지 않도록 수정됨), 프로세스별 원인 분석, 신뢰도 시스템, CPU/GPU 상관관계 분석, 증상 기반 진단, 정상 판정 근거, 재검사 방법 안내, 진단 기록, 리포트 저장(HTML), 안정성 테스트, 웹 버전 테스트 통합**

## 판매용 점검 리포트에 대해 정직하게 밝혀둘 것

이건 아직 "인증 서비스"가 아니라 **인증 서비스의 재료가 되는 기능**입니다.

- 실제로 신뢰받는 서비스가 되려면 서버 기반 서명/조회(QR 스캔 → 웹에서 원본 대조)가 있어야 하는데, 지금은 완전 로컬 앱이라 그 부분이 없습니다. 지금 QR은 "구매자가 판매자에게 같은 PC에서 재실행해달라고 요청해 직접 대조하는" 용도로만 씁니다.
- 법적 책임 관련 문구는 넣었지만 실제 법률 검토를 받은 문구는 아닙니다. 실제로 이 리포트를 유료 서비스로 팔려면 변호사 검토가 필요합니다.
- CPU는 OS에서 표준적으로 읽을 수 있는 시리얼이 없어서 모델명으로만 식별됩니다. GPU UUID도 NVIDIA만 지원합니다.
- 실제 조립 PC에서 확인한 결과, **GPU UUID와 저장장치 시리얼은 정상적으로 채워지지만 시스템 시리얼은 비어 있는 경우가 많습니다**(보드 제조사가 값을 안 넣기 때문). 그래서 대조용 식별값이 하나도 없는 PC도 있을 수 있고, 그런 경우 리포트에 경고 문구가 표시됩니다.
- 검증코드는 리포트 내용이 바뀌었는지는 확실히 잡아내지만, **이 앱을 가진 판매자가 검사 전에 값을 조작하는 것까지 막지는 못합니다**. 그건 서버 서명이 있어야 가능하고 지금은 없습니다.

## 이번 버전에도 구현하지 않은 것 (그리고 이유)

기획서 30장 전체를 문자 그대로 "완벽 구현"하는 건 이 세션 하나로는 불가능합니다.
아래는 의도적으로 제외한 항목과 이유입니다.

- **HDR / VRR 테스트** — OS/디스플레이가 실제로 HDR·VRR을 활성화했는지 정확히 읽으려면
  Windows의 DXGI/DirectX 디스플레이 API를 네이티브로 호출해야 합니다. Node 표준 라이브러리
  범위를 벗어나 이번엔 넣지 않았습니다.
- **Frame Skip 테스트** — 실제 프레임 드롭을 측정하려면 게임/렌더링 후킹이 필요해서 범위 밖입니다.
- **실제 지원 주사율 대비 진단** ("이 모니터는 144Hz를 지원하는데 60Hz로 설정됨" 같은 진단) — Win32
  `EnumDisplaySettingsEx`로 시도해봤으나 이 개발 환경에서는 실제 디스플레이 세션이 있는데도
  호출이 계속 실패했고(WMI의 `WmiMonitorListedSupportedSourceModes`는 EDID의 구식 표준 타이밍
  목록만 반환해 최신 모니터에서 오탐 위험이 큼을 실측으로 확인), 검증 못 한 채로 넣을 수 없어
  보류했습니다. 지금은 "현재 주사율이 60Hz 미만"인 경우만 진단합니다.
- **Color 정밀 테스트(색영역/캘리브레이션)** — 컬러미터 없이 소프트웨어만으로는 신뢰할 수
  없어서, 육안 확인용 그라데이션 테스트로 대체했습니다.
- **센서 기록 → 진단 엔진 자동 반영** — 실시간 모니터링의 "기록 시작"은 지금은 값을 남기고
  JSON으로 저장하는 것까지만 합니다. 기획서(22장)는 이 데이터를 "진단 엔진의 핵심 입력"으로
  쓰는 걸 목표로 하는데, 임의의 기록 구간에서 스파이크를 자동으로 찾아 원인을 추정하는 로직은
  이번엔 넣지 않았습니다(Correlation Engine이 지금 다루는 건 "오늘의 라이브 측정 vs 최근 며칠
  이벤트 로그"이지, 기록된 시계열 자체의 이상 탐지는 아닙니다).
- **설치 파일(.exe)/코드 서명/자동 업데이트/크래시 리포팅** — 코드 서명 인증서 구매,
  업데이트 서버 운영, Sentry 같은 크래시 리포팅 서비스 가입이 필요한 **인프라/비용이
  드는 영역**이라 코드로 대신할 수 없습니다. `electron-builder`를 추가하면 `.exe`
  패키징 자체는 가능하니, 원하시면 다음 단계로 만들어드릴 수 있어요.
- **Confidence를 통계적으로 검증하는 것** — 지금 점수는 "증거가 몇 개 겹치는가"를 사람이
  정한 가중치입니다. 실제 사용자 데이터로 검증된 확률이 아니라는 걸 분명히 해둡니다.
